# VISION.md

## What GameBoyStudio Is

**GameBoyStudio is an instant-play gaming platform for the web, built
controller-first.**

Games launch without installs or configuration, controls are immediately
understandable, and physical controllers are a first-class part of the
experience.

## Why It Exists

> **Remove the distance between wanting to play something and actually playing it.**

That sentence explains the entire roadmap. Today the distance is: see game →
play. Later: friend sends game → play. Then: join multiplayer → play.
Eventually: imagine game → create → play.

It is also why AI creation belongs here rather than being bolted on — it is the
same philosophy applied to the creator side.

```
PLAYER                        CREATOR

"I want to play that."        "I want this game to exist."
        ↓                              ↓
      PLAY                          CREATE
                                       ↓
                                     PLAY
```

## The Bigger Idea

GameBoyStudio starts with one simple experience:

**Open the website. Find a game. Press play.**

The early product begins with small retro games because they are lightweight,
controller-friendly, and a strong way to prove that browser gaming can feel
immediate and polished.

But GameBoyStudio is not fundamentally a Game Boy emulator site.

It is the beginning of a **web-native gaming platform** where games are easier to discover, start, play, share, play together, and eventually create.

The browser is the console.
The website is the home screen.
The games are the cartridges.

Over time, those games can include:

- classic games
- retro games from multiple systems
- homebrew games
- modern browser games
- indie games
- multiplayer games
- community-created games
- games made specifically for GameBoyStudio
- AI-assisted games

The technical origin of a game should eventually matter less than whether it is interesting and playable.

## Core Loop

GameBoyStudio should grow around four behaviors:

**PLAY → DISCOVER → CONNECT → CREATE**

Later, creation closes the loop:

**PLAY → DISCOVER → CONNECT → CREATE → PUBLISH → PLAY**

That loop is more important than supporting any single console.

## Why Start With Retro Games

Retro games let the platform solve the foundational problem first:

**Can playing a game on the web feel immediate, polished, and intentional?**

If that experience is weak, multiplayer, social features, AI, or a massive library will not save the product.

## Game Boy Is a Starting Identity, Not a Boundary

GameBoyStudio borrows the *qualities* that made portable gaming compelling —
immediate, simple, tactile, approachable, low-friction, easy to understand, pick
up and play.

It does not borrow the *limits*. Eight buttons, a 160x144 screen, tiny binaries
and single-sitting scope describe our starting content. They must never become
the specification of the platform. A future GameBoyStudio game may be large,
long, richly interactive, multiplayer, or three-dimensional.

The product should not permanently organize itself around Game Boy hardware.

A future user should be able to encounter an old game, a new multiplayer game, and a community-created game without feeling like they left the product.

## Controller-First, Not Controller-Only

Physical controllers are the platform's defining interaction and its strongest
design convention. The default GameBoyStudio game is completely playable with a
controller, and native games treat the standardized gamepad model as a
first-class target.

That is a default and a certification — **not** a prohibition. Games declare the
input profiles they require and support. The platform may host games that use
keyboard, pointer, touch, motion, or combinations, including asymmetric play
where different players use different devices.

See PLATFORM_DIRECTION.md for the input profiles and the Gamepad Native
definition.

## What GameBoyStudio Should Become

The strongest version is not:

> a website with many emulators

It is:

> a place where playable things live

A player comes because they want something to play.
A creator comes because they want to make something playable.
A friend comes because someone invited them into something.

Those motivations should eventually reinforce each other.

## AI Is Not the Product

AI should eventually reduce the distance between having a game idea and trying it.

The user should not feel like they are using an AI coding assistant.

They should feel like they are making a game.

A future creation loop could be:

1. Describe an idea.
2. Receive a playable version.
3. Play it immediately.
4. Modify it.
5. Invite friends to test it.
6. Publish it.
7. Let others discover it.

The important goal is shrinking:

**idea → playable game**

## Multiplayer Is More Than Retro Netplay

Multiplayer can eventually include:

- local multiple-controller play
- native multiplayer games
- private rooms
- invitations
- challenges
- asynchronous competition
- leaderboards
- tournaments
- creator-built multiplayer games

Old games do not all need to be forced into multiplayer.

New experiences can be built specifically for the platform.

## End State

A future GameBoyStudio library could contain:

- a classic game from decades ago
- a licensed retro title
- an indie game
- a four-player browser game
- a tiny experiment made by a student
- an AI-assisted game
- a game your friend made five minutes ago

All of them should share one property:

**you can press play.**
